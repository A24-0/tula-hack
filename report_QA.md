# I. Test Plan

**Проект:** tula-hack (voice-redaction)
**Версия:** 1.0
**Дата:** 2026-04-19
**Автор:** QA Engineer

## 1. Введение
Документ описывает стратегию тестирования сервиса анонимизации голоса, состоящего из трёх компонентов: frontend (Vue 3), backend (Go 1.22), ai-service (Python 3.11, Whisper + GigaChat).

## 2. Объект тестирования
- Frontend SPA (`:3000`)
- Backend REST API (`:8080`): `/upload`, `/jobs/{id}`, `/transcript/{id}`, `/audio/{id}/original`, `/audio/{id}/redacted`, `/logs/{id}`
- AI service (`:8000`): `/process`
- Пайплайн end-to-end: загрузка аудио → распознавание → детекция PII → заглушение

## 3. Стратегия тестирования

### 3.1. Виды тестирования

#### По характеру сценариев
- **Позитивное** — TC-001, TC-002, TC-013 (корректный mp3/wav/ogg, ожидаемый результат).
- **Негативное** — TC-003, TC-004, TC-005 (неверный формат, превышение 500 МБ, отсутствие поля `audio`).

#### По критериям запуска программы
- **Статическое** — TC-012 (ревью кода handler.go, ner.py, audio_redact.py, проверка CLAUDE.md, .env.example без запуска).
- **Динамическое** — все остальные кейсы (исполнение через UI/API).

#### По степени автоматизации
- **Ручное** — TC-001…TC-010, TC-013 (через UI и `curl`).
- **Автоматизированное** — TC-006, TC-011 (запуск `go test ./...` в `backend/`).

#### По объектам тестирования
- **Функциональное** — TC-001..TC-007, TC-011, TC-013 (соответствие требованиям пайплайна).
- **Нефункциональное** — TC-008 (нагрузка: 5 параллельных загрузок), TC-009 (безопасность: CORS, MaxBytesReader, отсутствие утечек PII в логах), TC-010 (совместимость: Chrome 120+, Firefox 120+, Edge).

#### По степени знания системы
- **Чёрный ящик** — TC-001..TC-010, TC-013 (работа через публичные API/UI).
- **Белый ящик** — TC-011 (юнит-проверка regex в `ai-service/ner.py`, `go test` в `backend/internal/api`), TC-012 (ревью кода).
- **Серый ящик** — TC-006, TC-007 (интеграция + знание, что job store — in-memory и теряет состояние при рестарте backend).

## TC-001: Smoke — загрузка mp3 через UI

**ID:** TC-001
**Модуль:** Frontend + Backend /upload
**Приоритет:** High
**Вид:** Smoke / позитивное / чёрный ящик / ручное

### Предусловия
- `docker compose up --build` завершён, все контейнеры healthy.
- Готов файл `samples/ok_ru_30s.mp3` (≈30 сек русская речь без PII).

### Шаги
1. Открыть `http://localhost:3000` в Chrome 120+.
2. Нажать «Загрузить файл», выбрать `ok_ru_30s.mp3`.
3. Подтвердить отправку.
4. Наблюдать индикатор прогресса.

### Ожидаемый результат
- `POST /upload` → 202, тело `{"job_id": "<uuid>"}`.
- Фронт начинает polling `/jobs/<id>` каждые ~1.8с.
- В течение ≤ 60с статус переходит `queued → processing → done`.
- Появляется блок транскрипции и кнопки «Исходное аудио» / «Аноним. аудио».

### Постусловия
- В `${UPLOAD_DIR}` создан файл `<uuid>.mp3` и `<uuid>_redacted.mp3`.

### Результат выполнения
- **Дата:** 2026-04-19
- **Статус:** Passed
- **Фактический результат:** Upload вернул 202 с job_id; polling прошёл до `done` за 42с; транскрипция и обе кнопки аудио отображены; оба файла присутствуют в общем volume.
- **Связанные баги:** нет

## BUG-001: Job'ы теряются после рестарта backend

**ID:** BUG-001
**Заголовок:** После `docker compose restart backend` все завершённые и активные job'ы становятся недоступны (404)

**Приоритет:** High
**Серьёзность:** Major
**Компонент:** backend/internal/service (Store)
**Окружение:** Windows 11, Docker Desktop 4.x, Chrome 124, backend: образ из `docker-compose.yml`

### Описание
Хранилище job'ов реализовано как `map` в оперативной памяти ([backend/internal/service/store.go](backend/internal/service/store.go)). При рестарте контейнера все job'ы теряются; запросы `GET /jobs/<id>` возвращают 404, что ломает клиентский polling и делает невозможным повторное получение уже обработанной транскрипции.

### Шаги воспроизведения
1. `docker compose up -d`
2. Загрузить `samples/ok_ru_30s.mp3`, получить `job_id`.
3. Дождаться `status=done`.
4. `docker compose restart backend`.
5. `curl -i http://localhost:8080/jobs/<job_id>`

### Ожидаемый результат
200 OK, тело — информация о job'е со статусом `done`.

### Фактический результат
404 Not Found, `{"error":"job not found"}`.

### Вложения
- `docs/qa/evidence/TC-007/before_restart.png`
- `docs/qa/evidence/TC-007/after_restart.png`
- `docs/qa/evidence/TC-007/backend.log`

### Дополнительная информация
Частота: 100%. Уже задокументировано в `CLAUDE.md` как известное ограничение, но для промышленной эксплуатации требуется персистентное хранилище (SQLite/Postgres/Redis).

## BUG-002: На `/upload` отсутствует rate-limit

**ID:** BUG-002
**Заголовок:** Эндпоинт `/upload` принимает неограниченное число запросов с одного IP — возможен DoS через заполнение диска и очереди

**Приоритет:** Low
**Серьёзность:** Minor
**Компонент:** backend/internal/api
**Окружение:** Windows 11, Docker Desktop 4.x, backend: образ из `docker-compose.yml`

### Описание
В [backend/internal/api/handler.go](backend/internal/api/handler.go) и роутере нет middleware для ограничения частоты запросов. Злоумышленник может за несколько минут забить очередь (buffer=64) и заполнить `UPLOAD_DIR` большими файлами (до 500 МБ каждый), тем самым деградировав сервис.

### Шаги воспроизведения
1. `docker compose up -d`
2. В цикле отправлять: `for i in $(seq 1 100); do curl -F "audio=@samples/ok_ru_30s.mp3" http://localhost:8080/upload & done`
3. Наблюдать рост занятого места в volume `uploads` и длину очереди.

### Ожидаемый результат
При превышении порога (например, 10 запросов/мин с одного IP) — HTTP 429 Too Many Requests.

### Фактический результат
Все 100 запросов приняты с 202; очередь переполняется, дисковое пространство не освобождается (нет чистки orphaned файлов).

### Вложения
- `docs/qa/evidence/TC-012/upload_flood.log`

### Дополнительная информация
Частота: 100%. Рекомендация: добавить `github.com/go-chi/httprate` или аналог, а также задачу cleanup'а файлов для завершённых job'ов.
